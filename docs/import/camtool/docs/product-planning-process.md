# 캠툴 제품 기획 운영 프로세스

작성 기준일: 2026-08-30

## 1. 목적

기능 아이디어를 반복해서 요청하거나 기획 범위를 확장하더라도 문서가 서로 중복되고
우선순위가 흔들리지 않도록 캠툴의 기획 작업을 하나의 운영 흐름으로 관리한다.

이 프로세스는 다음 문제를 방지한다.

- 같은 기능이 여러 문서에서 다른 이름과 상태로 관리되는 문제
- 기획 요청마다 새로운 후보만 늘고 실행 순서가 정해지지 않는 문제
- 기존 도구의 사용성 개선과 리뉴얼이 신규 URL보다 낮게 취급되는 문제
- 아이디어가 문서에 있다는 이유만으로 구현 승인으로 오해되는 문제
- 구현 후 로드맵과 기획 문서가 과거 상태로 남는 문제
- AdSense, 다국어, 개인정보와 Playwright 조건이 구현 직전에 뒤늦게 추가되는 문제

## 3. 기획 요청 분류

새 요청을 받으면 먼저 아래 네 유형 중 하나로 분류한다. 모든 유형에서 새 도구를
찾기 전에 기존 공개 도구가 같은 문제를 더 잘 해결하도록 개선할 수 있는지 확인한다.

### A. 기존 개선·리뉴얼 또는 아이디어 확장

예: “타이머 시간을 직접 정하고 싶어”, “기능을 더 많이 제안해줘”

- 기존 아이디어 카탈로그와 중복을 검색한다.
- 변경 형태를 `개선`, `리뉴얼`, `기존 route 기능 확장`, `신규 도구` 중 하나로
  먼저 분류한다.
- 개선은 현재 흐름의 마찰을 줄이고, 리뉴얼은 같은 route와 목적을 유지하면서 입력·
  결과·시각 구조를 다시 설계한다. 독립 검색 문제일 때만 신규 URL을 검토한다.
- 기존 후보의 옵션 확장이면 새 항목을 만들지 않고 해당 항목을 보강한다.
- 입력과 결과가 명확히 다른 문제만 새 후보로 등록한다.
- 후보 수보다 검색 의도와 최소 결과를 우선한다.

### B. 후보 평가

예: “무엇부터 하는 게 좋아?”, “파일 변환 중 현실적인 것은?”

- 후보의 검색 의도, 로컬 처리, 개발비, 유지비와 정확성 위험을 비교한다.
- 휴대폰 계산기, 운영체제와 브라우저 기본 기능으로 30초 안에 해결되는지 먼저
  비교한다.
- 구현이 쉽거나 검색어가 있다는 이유만으로 통과시키지 않는다. 오류 방지, 여러
  단계 자동화, 비교·검증, 복사·다운로드처럼 기본 기능보다 나은 결과가 최소 두
  가지 있어야 한다.
- `feature-opportunity-plan.md` 또는 해당 도메인 기획을 갱신한다.
- 평가만으로 로드맵을 `계획됨`으로 바꾸지 않는다.

#### 최소 필요성·기본 기능 대체성 게이트

신규 도구와 기존 기능의 독립 URL 승인은 우선 다음 질문을 통과해야 한다.

1. 사용자가 휴대폰 기본 기능 대신 이 문제를 별도로 검색할 이유가 있는가?
2. 기본 계산기·운영체제·브라우저로 해결할 때 몇 단계가 필요하고 캠툴은 이를
   얼마나 줄이는가?
3. 단순 계산값 외에 오류 방지, 복합 규칙, 비교·검증, 복사·다운로드 중 최소 두
   가지 고유 결과를 제공하는가?
4. 반복 빈도나 한 번 틀렸을 때의 비용이 별도 도구를 찾을 만큼 충분한가?
5. 신규 URL보다 기존 route의 작은 옵션으로 제공하는 편이 낫지 않은가?

한 번의 나눗셈·곱셈·덧셈만 대신하는 후보는 기본적으로 제외한다. 독립 URL로
승인하려면 기본 기능 대비 줄어드는 단계와 고유 결과를 제안 카드에 구체적으로
기록해야 한다.

### C. 실행 사이클 편성

예: “다음에 할 것들을 기획해줘”, “5단계로 나눠줘”

- 이미 평가된 후보만 실행 묶음에 넣는다.
- 한 묶음은 한꺼번에 구현할 목록이 아니라 순차 검증 순서로 작성한다.
- 각 기능의 진행·중단 조건과 선행 작업을 함께 적는다.
- 현재 사이클 문서를 갱신하며 같은 목적의 새 문서를 만들지 않는다.

### D. 구현 승인

예: “1번 진행해줘”, “Excel·CSV 변환기를 만들어줘”

- 선택한 기능의 제안 카드를 템플릿으로 완성한다.
- 로드맵 상태를 `진행 중`으로 바꾼다.
- 도구 키, route, 번역 키와 검색 의도를 도메인 사전에 등록한다.
- 구현·한영 콘텐츠·테스트·문서·배포 준비를 같은 작업 범위로 진행한다.

## 4. 상태 전환

```text
수집됨 → 평가됨 → 계획됨 → 진행 중 → 출시됨 → 관찰 중
   └──────────────→ 보류
출시됨/관찰 중 ──→ 개선 예정 또는 종료 검토
```

저장소의 공식 로드맵 상태는 기존 다섯 값만 사용한다. `수집됨`, `평가됨`, `관찰 중`,
`개선 예정`은 기획 인덱스나 후보 카드의 작업 단계이며 로드맵 상태를 새로 늘리지 않는다.

| 단계 | 완료 조건 | 갱신 대상 |
| --- | --- | --- |
| 수집됨 | 대표 문제와 최소 결과가 있음 | 아이디어 카탈로그 |
| 평가됨 | 중복·비용·위험·로컬 처리 판단 완료 | 후보 평가 문서 |
| 계획됨 | 사용자가 다음 구현 대상으로 합의 | 제품 로드맵 |
| 진행 중 | 구현 작업을 실제 시작 | 로드맵·도메인 사전 |
| 출시됨 | 빌드·테스트·Playwright·배포와 운영 확인 완료 | 로드맵·기획 문서 |
| 관찰 중 | 지표와 오류를 정해진 기간 확인 | 기획 인덱스·결정 기록 |
| 보류 | 이유와 재검토 조건이 명시됨 | 제품 로드맵 |

## 5. 반복 기획 요청 처리 순서

1. `planning-index.md`에서 현재 기준 문서와 열린 다음 행동을 확인한다.
2. `product-roadmap.md`에서 후보 상태와 이미 합의된 우선순위를 확인한다.
3. 모든 기획 문서에서 후보명·별칭·검색 의도를 검색해 중복을 찾는다.
4. 최소 필요성·기본 기능 대체성 게이트로 별도 도구가 필요한지 먼저 판정한다.
5. 요청을 기존 개선·리뉴얼 또는 아이디어 확장, 후보 평가, 사이클 편성, 구현 승인
   중 하나로 분류한다.
6. 새 내용이 어느 단일 기준 문서에 속하는지 결정한다.
7. 기존 문서로 충분하면 새 문서를 만들지 않고 해당 섹션을 갱신한다.
8. 새 문서가 필요하면 목적, 대체하지 않는 문서와 종료 조건을 첫 부분에 적는다.
9. README, 기획 인덱스, 로드맵과 도메인 사전의 링크·요약을 동기화한다.
10. 구현되지 않은 후보가 코드, sitemap과 공개 URL에 들어가지 않았는지 확인한다.
11. 문서 검증과 기능 단위 커밋 후 GitHub에 반영한다.

## 6. 새 문서를 만드는 기준

다음 조건을 모두 만족할 때만 별도 기획 문서를 만든다.

- 기존 문서의 한 섹션으로 관리하기에는 독립적인 의사결정 주기가 있다.
- 최소 3개 이상의 연관 후보 또는 여러 단계의 실행 계약을 가진다.
- 문서 소유 목적과 종료·통합 조건을 설명할 수 있다.
- README와 `planning-index.md`에서 어디에 위치하는지 연결할 수 있다.

다음 경우에는 새 문서를 만들지 않는다.

- 기존 후보 하나의 옵션이나 설명만 늘리는 경우
- 같은 후보를 다른 표현으로 다시 나열하는 경우
- 단순 구현 체크리스트가 기존 승인 템플릿으로 충분한 경우
- 상태만 변경하면 되는 경우

## 7. 후보 제안 카드

각 기능은 구현 승인 전에
[`templates/feature-proposal.md`](./templates/feature-proposal.md)를 복사해 작성하거나,
같은 필드를 기준 기획 문서의 후보 섹션에 채운다.

필수 필드는 다음과 같다.

- 표준 기능명과 별칭
- 한국어·영어 대표 검색 의도
- 사용자가 한 번의 방문에서 얻는 결과
- 기존 캠툴 도구와 다른 점
- 최소 입력·결과·복사 또는 다운로드 흐름
- 로컬 처리 범위와 개인정보 안내
- 정확성 기준, 경계값과 알려진 한계
- 명시적 제외 범위
- AdSense placement와 금지 영역
- 1440·390·320px, 키보드, 오류와 광고 on/off 테스트
- 초기 개발비, 사용량 비용, 유지비와 라이선스
- 변경 형태와 기존 route 재사용 여부
- 출시 후 관찰 지표와 보류·중단 조건

## 8. 우선순위 회의 규칙

실제 회의가 없더라도 한 번의 기획 작업을 작은 우선순위 회의처럼 처리한다.

1. 현재 `진행 중` 항목이 있으면 새 후보보다 완료 또는 보류 결정을 먼저 한다.
2. `계획됨` 항목이 여러 개면 기존 순서를 바꾸는 근거를 기록한다.
3. 한 사이클에는 신규 URL 하나를 기본으로 한다.
4. 각 사이클은 기존 도구의 오류·사용 마찰과 개선 후보를 먼저 검토한다. 기존 도구
   확장이 신규 도구보다 낮은 비용으로 같은 검색 문제를 해결하면 이를 우선한다.
5. 파일 도구는 선행 프로토타입과 모바일 메모리 한도를 먼저 확정한다.
6. 광고 수익 예상만으로 우선순위를 높이지 않는다.
7. Search Console과 실제 오류 근거가 있으면 감각적인 후보 수보다 우선한다.

### 특별 라이선스·외부 계약 제외 정책

다음 중 하나가 핵심 구현에 필요하면 활성 기획, 실행 사이클과 즉시 착수 목록에서
제외하고 로드맵에 보류 이유만 남긴다.

- 상용 SDK·폰트·템플릿·데이터 또는 유료 라이선스 구매
- GPL·AGPL 등 배포물이나 서비스에 추가 공개 의무를 만드는 copyleft 조건
- 별도 사용 허가, 제휴 승인, API 키·계정 또는 사용량별 유료 계약
- 특허·코덱·독점 파일 형식처럼 재배포 권리가 불명확한 구현
- 라이선스가 없거나 호환 여부를 명확히 확인할 수 없는 코드·에셋
- 화면 내 별도 저작권 고지나 광고·기능 배치 제약을 요구하는 자산

기본 허용 범위는 브라우저 표준 API, 프로젝트가 직접 작성한 코드·CSS, 직접 만든
에셋과 현재 설치된 의존성이다. 새 패키지는 일반적인 permissive 라이선스이고 별도
결제·계정·런타임 계약이 없으며 번들·보안상 이점이 분명할 때만 예외적으로 검토한다.
즉시 착수 후보는 새 런타임 의존성 없이 구현 가능한 범위로 한정한다.

원래 후보에서 제한 요소를 제거한 축소 MVP가 독립적으로 유용하면 축소안을 새 기준
범위로 평가할 수 있다. 축소하면 핵심 결과가 사라지는 후보는 유지하지 않는다.

## 9. 구현 시작 게이트

다음 항목이 모두 충족되지 않으면 코드 작업을 시작하지 않는다.

- 사용자가 특정 후보 또는 단계의 구현을 명확하게 요청했다.
- 제품 로드맵 상태가 `진행 중`으로 바뀌었다.
- 기능 제안 카드의 필수 필드가 작성됐다.
- 한국어·영어 route와 대표 검색 의도가 충돌하지 않는다.
- 로컬 처리, 외부 전송과 개인정보 안내가 결정됐다.
- 광고 placement와 Playwright 계약이 결정됐다.
- 새 런타임 의존성 없이 구현하거나, 특별 라이선스·외부 계약 제외 정책의 예외 기준을
  충족한다.
- 도메인 사전에 실제 코드 식별자와 경로를 등록했다.

## 10. 출시와 관찰 게이트

### 출시 전

- 기능, 한영 콘텐츠, 메타데이터, canonical, alternate, sitemap을 동기화한다.
- 정상·빈·잘못된 입력·경계·복구 흐름을 테스트한다.
- 데스크톱, 모바일, 320px과 광고 off/on을 Playwright로 확인한다.
- 빌드·린트·전체 테스트·배포 사전 검사를 통과한다.
- 로드맵과 제안 카드가 실제 범위와 일치한다.

### 출시 후

- 운영 URL의 언어 전환, 내부 링크와 대표 정상 흐름을 다시 확인한다.
- 로드맵을 `출시됨`으로 바꾸고 기준일을 기록한다.
- 기획 인덱스에 관찰 기간과 다음 점검 항목을 적는다.
- 검색 노출이 없으면 유사 페이지를 늘리지 않고 색인·제목·문제 적합성을 먼저 본다.
- 오류가 반복되면 기능 추가보다 한도·안내·복구 흐름을 먼저 개선한다.

## 11. 정기 정리 규칙

반복 요청이 없더라도 다음 시점에 기획 문서를 정리한다.

- 신규 기능 출시 직후
- 공개 도구가 8·12·21개 임계점에 도달할 때
- 같은 후보가 세 문서 이상에서 장문으로 반복될 때
- 작성일로부터 90일이 지난 경쟁 정보나 비용 정보가 사용될 때
- 보류 후보를 다시 제안할 때

정리 시 오래된 문서를 삭제하기보다 상태, 대체 문서와 보류 이유를 남긴다. 완전히
대체된 문서는 첫 부분에 `대체됨` 표시와 새 기준 문서 링크를 둔다.

## 12. 완료 보고 형식

기획 작업을 마칠 때는 다음을 짧게 보고한다.

```text
요청 유형:
갱신한 단일 기준 문서:
추가·통합·보류한 후보:
로드맵 상태 변경:
다음 승인 필요 항목:
검증과 Git 반영:
```

이 형식을 사용하면 다음 세션에서도 기획이 어디까지 진행됐고 무엇을 결정해야 하는지
대화 기록에 의존하지 않고 저장소 문서만으로 복원할 수 있다.
