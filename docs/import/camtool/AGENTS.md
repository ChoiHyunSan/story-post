# CAMTOOL PROJECT GUIDE

이 문서는 저장소 전체에 적용되는 개발 규칙이다. 하위 폴더에 더 구체적인
`AGENTS.md`가 생기면 해당 폴더에서는 하위 문서가 우선한다.

## 0. 모든 작업의 필수 준수 게이트

이 저장소에서 수행하는 조사, 문서 작성, 코드 수정, 리팩터링, 배포 준비와
긴급 수정은 작업 규모와 관계없이 이 문서의 규칙을 따른다. 빠른 수정이나 사용자
요청을 이유로 사전 확인, 연관 문서 갱신, 검증 또는 커밋 규칙을 생략하지 않는다.

### 작업 시작 전

1. 저장소 루트와 작업 경로에 적용되는 모든 `AGENTS.md`를 확인한다.
2. `docs/domain-glossary.md`에서 변경 대상 개념·식별자·경로를 확인한다.
3. 기능 또는 제품 범위를 다루면 `docs/product-roadmap.md`와 해당 기획 문서를
   확인하고 실제 상태와 문서 상태를 맞춘다.
4. 변경 전에 코드, 테스트, README, 도메인 사전, 로드맵, 기획 문서,
   `.env.example`, sitemap, 메타데이터와 배포 문서 중 함께 갱신할 파일을
   식별한다.
5. 현재 Git 상태를 확인하고 사용자의 기존 변경과 이번 작업 범위를 분리한다.

### 구현 중

- 등록된 도메인명, 코드 식별자, 번역 키와 경로를 재사용한다.
- 코드만 먼저 바꾸고 연관 문서를 나중 작업으로 미루지 않는다. 구현과 문서,
  한국어·영어 문구, 테스트를 같은 작업 범위에서 동기화한다.
- 로그인, 데이터베이스, 외부 API, 예제 코드와 초기 템플릿 파일은 실제 제품
  요구가 있을 때만 유지한다. 사용하지 않는 스캐폴드와 의존성은 완료 전에
  제거한다.
- 새 공개 URL이나 기능 범위 변경은 카탈로그, 도메인 사전, 로드맵, 메타데이터,
  canonical, `hreflang`, sitemap, 구조화 데이터와 관련 테스트를 함께 확인한다.
- 규칙과 구현이 충돌하면 규칙을 무시하지 말고 충돌 원인을 해결하거나 사용자에게
  명시적으로 보고한다.

### 완료 및 Git 반영 전

1. 변경된 개념과 실제 경로가 도메인 사전과 일치하는지 다시 검색한다.
2. README, 로드맵, 기획·배포 문서의 기능 범위와 상태가 실제 구현과 일치하는지
   확인한다.
3. 한국어·영어 문구와 메타데이터가 함께 갱신됐는지 확인한다.
4. 최소 `pnpm build`와 `pnpm lint`를 실행하고, 관련 테스트와 배포 사전 검사가
   있으면 함께 실행한다.
5. 빌드 산출물, 비밀값, 로컬 상태와 사용하지 않는 템플릿 파일이 Git 변경에
   포함되지 않았는지 확인한다.
6. `docs/git-commit-conventions.md`에 따라 변경을 하나의 의도 단위로 나누고,
   staged diff를 검토한 뒤 각 커밋이 빌드 가능한 상태인지 확인한다.
7. 사용자가 push를 요청했다면 원격 반영 후 로컬 브랜치와 원격 브랜치가
   동기화됐는지 확인한다.

### 문제 해결 이력과 회귀 방지

- 사용자 흐름을 막거나 잘못된 결과를 만든 문제, 특정 환경에서만 드러난 회귀,
  기존 검증을 빠져나간 문제는 수정과 같은 변경에서
  [`docs/problem-resolution-history.md`](docs/problem-resolution-history.md)에 기록한다.
- 기록은 `증상·재현 → 직접 원인 → 검출 실패 원인 → 수정 → 해결 검증`을 포함하고
  [`docs/templates/problem-resolution-record.md`](docs/templates/problem-resolution-record.md)를
  사용한다. 확정되지 않은 원인을 사실처럼 작성하지 않는다.
- 재현 가능한 실패 조건은 자동 테스트로 고정한다. 여러 화면에 적용되는 조건은
  Playwright 체크리스트에도 승격해 다음 관련 작업의 필수 회귀 계약으로 사용한다.
- 수정 전 이력에서 변경 영역과 관련된 회귀 계약을 찾고 테스트 범위에 포함한다.
  같은 원인이 재발하면 새 기록을 복제하지 말고 기존 기록에 재발과 추가 조치를
  누적한다.
- 사용자 영향과 재발 방지 가치가 없는 단순 오탈자는 이력에 기록하지 않는다.

### Playwright 브라우저 검증

- UI, 상호작용, 라우팅, 다국어, 반응형 스타일, 메타데이터 또는 배포 결과를
  변경·확인할 때는 반드시
  [`docs/playwright-validation-checklist.md`](docs/playwright-validation-checklist.md)를
  먼저 읽고 적용한다.
- 실행 전 [`docs/problem-resolution-history.md`](docs/problem-resolution-history.md)에서
  변경 영역의 회귀 계약을 확인하고 결과 기록에 적용한 incident ID를 남긴다.
- 화면 변경은 영향을 받는 경로의 데스크톱·모바일·`320px` 최소 폭과 대표 정상
  흐름, 잘못된 입력, 키보드 탐색, 콘솔 오류를 Playwright로 확인한다.
- 모바일 검증은 단순 가로 overflow 측정으로 끝내지 않는다. `390×844`와
  `320×720`에서 메뉴·드로어·모달의 실제 높이와 스크롤, 핵심 입력·버튼·결과의
  가시성 및 대표 상호작용 완료 여부를 확인한다.
- 모바일 메뉴는 열린 drawer가 헤더 아래 남은 viewport를 채우고 내부 마지막
  링크까지 스크롤 가능한지 확인한다. 제목만 보이거나 drawer 높이가 접히면
  필수 실패로 처리한다.
- 공통 레이아웃, 번역 체계, 전역 스타일 또는 배포 설정 변경은 모든 공개 경로의
  스모크 테스트와 각 도구의 대표 정상 흐름을 확인한다.
- 재배포 작업은 저장소 검증과 배포가 성공한 뒤 운영 URL에서 언어 전환, 내부
  링크, 반응형 화면, 변경된 기능의 대표 흐름을 다시 확인한다.
- 결과에는 대상 커밋·URL·뷰포트·통과·실패·해당 없음과 이유를 기록한다. 필수
  항목이 실패했거나 확인되지 않은 상태에서는 완료 또는 배포 성공으로 보고하지
  않는다.

위 항목 중 하나라도 충족하지 못하면 작업을 완료로 보고하지 않는다. 검증할 수
없는 항목은 통과한 것으로 간주하지 말고 남은 위험이나 사용자 확인 필요 사항으로
명시한다.

## 필수 도메인 사전

- 기능이나 콘텐츠를 수정하기 전에 반드시
  [`docs/domain-glossary.md`](docs/domain-glossary.md)를 확인한다.
- 기획의 한국어 개념명, 영문 도메인명, 코드 식별자와 경로는 사전을 단일
  기준점으로 삼는다.
- 새 기능, 콘텐츠, route, 상태값, 환경변수, 광고 배치를 추가하면 구현과 같은
  변경에서 사전 항목을 추가한다.
- 이름 변경·통합·삭제 시 코드와 사전을 함께 갱신한다. 검색 호환성이 필요한
  이전 이름은 사전의 별칭 또는 `폐기된 이름`에 남긴다.
- 사전에 이미 있는 개념에 새 약어나 동의어를 만들지 말고 등록된 식별자를
  재사용한다.
- 코드 리뷰에서는 변경된 개념이 사전에 반영됐는지를 완료 조건으로 확인한다.

## 필수 Git 커밋 규칙

- 커밋 전 반드시
  [`docs/git-commit-conventions.md`](docs/git-commit-conventions.md)를 따른다.
- 커밋 형식은 `<type>(<scope>): <summary>`를 사용하고 적절한 type과 도메인
  scope를 선택한다.
- 하나의 커밋에는 하나의 구현 기능 또는 하나의 수정 의도만 포함한다.
- 기능에 직접 필요한 테스트, 콘텐츠, 도메인 사전 변경은 구현과 같은 커밋에
  포함한다.
- 관계없는 변경은 stage 단계에서 분리하고, 각 커밋이 빌드 가능한 상태인지
  확인한다.
- main 브랜치에 `WIP`, `update`, `fix bug`처럼 의미가 불분명한 커밋을 만들지
  않는다.

## 필수 제품 로드맵

- 추가 기능 아이디어와 우선순위는
  [`docs/product-roadmap.md`](docs/product-roadmap.md)에서 관리한다.
- 로드맵에 기록된 항목은 검토 대상이며, 사용자 요청이나 합의된 작업 범위 없이
  코드에 바로 반영하지 않는다.
- 기능 작업을 시작하는 변경에서 상태를 `진행 중`으로 바꾸고, 검증과 배포 준비가
  끝나면 `출시됨`으로 갱신한다.
- 새 아이디어는 문제, 기대 효과, 최소 범위를 짧게 기록한다. 상세 구현 방식은
  실제 작업을 시작할 때 도메인 사전과 코드 가까이에서 결정한다.
- 기능을 보류하거나 제외하면 삭제하지 말고 상태와 이유를 남긴다.
- README의 로드맵 링크를 유지해 기획 현황을 쉽게 찾을 수 있게 한다.

## 필수 제품 기획 프로세스

- 반복적인 아이디어 제안, 후보 평가, 우선순위 조정, 단계 분할과 구현 승인 작업은
  [`docs/product-planning-process.md`](docs/product-planning-process.md)를 따른다.
- 작업 시작 시 [`docs/planning-index.md`](docs/planning-index.md)에서 현재 기준 문서와
  결정 대기 항목을 확인한다.
- 새 기획 요청은 아이디어 확장, 후보 평가, 실행 사이클 편성, 구현 승인 중 하나로
  분류하고 해당 단일 기준 문서를 갱신한다.
- 기획은 신규 URL 추가만 뜻하지 않는다. 기존 도구의 오류·마찰 개선, 기능 확장,
  정보 구조와 시각 리뉴얼을 신규 도구와 동등한 후보로 평가하며, 더 작은 비용으로
  같은 사용자 문제를 해결하면 기존 route 개선을 우선한다.
- 상용·유료 라이선스, copyleft 공개 의무, 별도 사용 허가, 유료 API 계약, 특허·코덱
  또는 재배포 권리 확인이 필요한 후보는 기본 기획과 즉시 착수 목록에서 제외한다.
  범위를 브라우저 표준 API, 자체 코드·에셋과 현재 의존성만으로 줄일 수 있을 때만
  축소안으로 다시 평가한다.
- 새 의존성은 MIT·BSD·ISC·Apache-2.0처럼 일반적인 permissive 라이선스이고 별도
  결제·계정·사용량 계약·화면 내 고지 의무가 없을 때만 예외적으로 검토한다. 즉시
  착수 후보는 원칙적으로 새 런타임 의존성을 추가하지 않는다.
- 기존 문서로 관리 가능한 요청에 새 기획 문서를 만들지 않는다. 새 문서가 필요하면
  목적, 기존 문서와의 경계와 종료·통합 조건을 명시하고 기획 인덱스를 함께 갱신한다.
- 같은 후보의 설명을 여러 문서에 복사하지 않고 기준 문서의 요약과 링크를 사용한다.
- 구현 승인 전에는 [`docs/templates/feature-proposal.md`](docs/templates/feature-proposal.md)의
  필수 항목을 작성하고 로드맵 상태, 도메인 사전, 광고·Playwright 계약을 동기화한다.
- 기획 작업 완료 시 기획 인덱스의 최신 검토일, 현재 결정 대기와 최근 완료 항목이
  실제 문서 상태와 일치하는지 확인한다.

## 1. 제품 원칙

- 캠툴은 사용자가 검색으로 들어와 가입 없이 즉시 사용하고 나갈 수 있는 가벼운
  웹 도구 모음이다.
- 한 화면은 한 가지 문제를 명확하게 해결해야 한다.
- 새 도구는 `입력 → 즉시 결과 → 복사 또는 다운로드` 흐름을 한 페이지 안에서
  끝내고, 처음 방문한 사용자가 설명 없이도 3분 안에 사용할 수 있어야 한다.
- 각 도구는 검색 의도가 분명한 독립 URL, 고유한 제목과 설명을 가진다.
- 재방문, 알림, 장기 기록이 핵심인 기능은 캠툴의 우선 범위로 두지 않는다.
- 로그인, 서버 저장, 외부 API는 실제 요구가 생기기 전까지 추가하지 않는다.
- 사용자가 입력한 과제, 이름, 원고 등의 내용은 기본적으로 브라우저 밖으로
  전송하지 않는다.
- 저장이 필요하면 먼저 `localStorage`로 충분한지 검토하고, 사용 여부를 UI에
  명시한다.
- 기능 수보다 빠른 진입, 쉬운 이해, 모바일 사용성을 우선한다.

### 다국어 원칙

- 한국어는 기존 경로(`/`, `/timer`)를 유지하고 영어는 `/en`, `/en/timer`처럼
  `/en` 접두 경로를 사용한다.
- 언어별 페이지는 자동 리다이렉트하지 않고 같은 도구의 언어 전환 링크를
  제공한다.
- 한 페이지의 주요 콘텐츠와 내비게이션은 한 언어로 통일한다.
- 새 사용자 문구와 메타데이터는 `ko`, `en`을 같은 변경에서 함께 작성한다.
- 언어, 경로와 번역 키는 `app/i18n`에서 관리하고 기능 로직에 locale 분기를
  흩뜨리지 않는다.
- 언어별 페이지는 서로를 `hreflang` alternate로 연결하고 각 언어 URL을
  sitemap에 포함한다.

## 2. 기본 기술 스택

- React 19 + TypeScript strict mode
- Vinext의 App Router 호환 구조
- Vite 및 Cloudflare Worker 호환 빌드
- Tailwind CSS 4와 프로젝트 CSS 토큰
- 서버 저장이 필요할 때만 Drizzle/D1 사용
- 패키지 매니저는 `pnpm`만 사용하고 `pnpm-lock.yaml`을 함께 갱신한다.

기존 스택을 임의로 교체하거나 같은 목적의 상태 관리·스타일링 라이브러리를
중복 도입하지 않는다.

## 3. 디렉터리 구조

```text
app/
  <route>/page.tsx          # 라우팅, 메타데이터, 화면 조합
  components/
    ads/                    # 광고 스크립트와 광고 슬롯
    layout/                 # 헤더, 푸터, 페이지 셸
    ui/                     # 도메인을 모르는 작은 공통 UI
  config/                   # 환경변수 해석과 애플리케이션 설정
  content/                  # 메뉴, 라벨, 안내문 등 정적 콘텐츠
  features/
    <domain>/               # 규모가 커진 도구의 UI·상태·계산 로직
      components/
      model.ts
      utils.ts
  globals.css               # 전역 토큰, 레이아웃, 공통 반응형 규칙
db/                         # 실제 영속 데이터가 도입될 때만 사용
tests/                      # 사용자 행동과 결과 중심 테스트
public/                     # 정적 이미지, 아이콘, 소셜 미리보기
```

### 의존 방향

- `page.tsx`는 기능과 레이아웃을 조합하되 복잡한 계산을 직접 소유하지 않는다.
- `features/<domain>`은 다른 도메인의 내부 파일을 직접 참조하지 않는다.
- 공통 컴포넌트는 특정 도구의 이름이나 규칙을 알지 못해야 한다.
- 메뉴·도구명·경로처럼 여러 화면에서 반복되는 값은 `app/content`에 한 번만
  정의한다.
- 환경변수는 컴포넌트에서 직접 읽지 않고 `app/config`에서 검증해 노출한다.
- 재사용되지 않는 코드를 성급하게 공통화하지 않는다. 두 곳 이상에서 같은
  의미로 반복될 때 추출한다.

### 기능 분리 기준

다음 중 하나에 해당하면 `page.tsx`에서 `features/<domain>`으로 분리한다.

- 파일이 약 150줄을 넘으며 UI와 계산 로직이 섞이는 경우
- 독립 테스트가 필요한 계산, 포맷팅 또는 상태 전이가 있는 경우
- 같은 기능을 홈, 상세 페이지 등 두 화면 이상에서 사용하는 경우

## 4. TypeScript와 React 규칙

- `any`를 사용하지 않는다. 외부 입력은 `unknown`에서 검증한다.
- 도메인 타입은 사용하는 기능 가까이에 두고, 공유 타입만 별도 파일로 옮긴다.
- 파생 값은 원본 상태로부터 계산하고 같은 값을 별도 state로 중복 저장하지
  않는다.
- 이벤트 핸들러는 `handleStart`, `handleChangeMode`처럼 행동을 드러내는 이름을
  사용한다.
- boolean은 `is`, `has`, `can`, `should` 접두사를 사용한다.
- 컴포넌트는 PascalCase, 함수·변수는 camelCase, 상수는 필요한 경우에만
  UPPER_SNAKE_CASE를 사용한다.
- 브라우저 API가 필요한 파일에만 `"use client"`를 선언한다.
- 타이머와 이벤트 리스너는 effect cleanup에서 반드시 해제한다.
- 무작위 결과, 날짜 계산 등은 작은 유틸 함수로 분리해 의도를 드러낸다.
- 내부 페이지 이동에는 프레임워크의 `Link`를 사용한다.

## 5. 콘텐츠와 UI 규칙

- 사용자에게 보이는 기본 문구는 자연스러운 한국어로 작성한다.
- 사용자 문구는 컴포넌트에 `ko`/`en` 객체로 직접 작성하지 않고
  `app/i18n/messages`의 번역 키로 관리한다.
- 번역 키는 `image_converter.upload_title`처럼 `<domain>.<meaning>` 형식을
  사용하고, 컴포넌트에서는 `createTranslator(locale)`로 조회한다.
- 화면 언어는 URL에서 결정된 `Locale`과 문서의 `lang`을 기준으로 한다.
  client component에서 `navigator.language`를 직접 읽어 서버 렌더 결과를
  덮어쓰지 않는다.
- 동적 값은 문구를 조합하지 말고 `{count}`, `{name}` 같은 사전의 자리표시자와
  번역 함수의 variables를 사용한다.
- 새 키는 한국어·영어 사전에 같은 변경으로 추가한다. 한국어 키 집합을 기준으로
  다른 언어 사전의 누락과 잘못된 키를 TypeScript가 검사하도록 유지한다.
- 버튼은 명사보다 행동을 사용한다. 예: `계산`, `복사`, `다시 시작`.
- 같은 개념의 이름과 설명은 `app/content`의 카탈로그를 재사용한다.
- 빈 상태, 잘못된 입력, 실행 중, 완료 상태를 모두 설계한다.
- 모바일 320px 이상, 키보드 탐색, 포커스 표시, reduced-motion을 지원한다.
- 색상만으로 상태를 전달하지 말고 텍스트나 형태를 함께 사용한다.
- 새 이미지가 꼭 필요하지 않으면 타이포그래피와 CSS 표현을 우선한다.

## 6. CSS 규칙

- 전역 색상·간격·그림자 값은 `:root` 토큰을 우선 사용한다.
- 클래스명은 역할을 설명하는 kebab-case로 작성한다.
- 기능 전용 스타일은 `globals.css`에서 도메인별 섹션으로 묶는다. 기능 규모가
  커지면 해당 feature의 CSS module로 이동한다.
- `!important`는 접근성 설정이나 외부 광고 스타일 충돌처럼 이유가 명확할
  때만 사용한다.
- 고정 높이보다 자연스러운 콘텐츠 흐름을 우선하되, 광고 영역은 레이아웃
  이동을 줄이기 위해 최소 높이를 예약한다.

## 7. 주석 규칙

- 주석은 적극적으로 사용할 수 있지만 코드가 이미 말하는 내용을 반복하지
  않는다.
- 비정상적인 제약, 브라우저 차이, 시간 동기화, 계산 근거, 외부 서비스 요구사항
  등 `왜`가 필요한 곳에 한두 문장으로 남긴다.
- 함수 전체를 설명하는 긴 블록 주석보다 복잡한 분기 바로 위의 짧은 주석을
  선호한다.
- 오래된 코드나 TODO를 주석으로 보관하지 않는다. TODO에는 해결 조건이나
  이슈 번호를 함께 적는다.

## 8. Google AdSense 구조

- 광고 관련 코드는 `app/components/ads`와 `app/config/ads.ts` 밖으로 흩뜨리지
  않는다.
- 페이지는 `AdSlot`의 placement만 선택한다. 게시자 ID와 슬롯 ID를 직접 쓰지
  않는다.
- 실제 값은 `.env.example`에 정의된 `NEXT_PUBLIC_ADSENSE_*` 환경변수로 주입한다.
  `NEXT_PUBLIC_` 값은 브라우저에 공개되므로 비밀값을 넣지 않는다.
- `NEXT_PUBLIC_ADSENSE_ENABLED=true`, 유효한 client ID, 해당 placement의 slot
  ID가 모두 있을 때만 광고를 렌더링한다.
- AdSense 스크립트는 루트 레이아웃에서 한 번만 로드한다.
- 광고가 꺼져 있으면 슬롯은 DOM과 레이아웃 공간을 만들지 않는다.
- 광고가 켜져 있으면 banner, rail 등 배치별 최소 높이를 확보해 CLS를 줄인다.
- 광고를 콘텐츠나 버튼처럼 보이게 만들지 않으며 `광고` 접근성 라벨을 유지한다.
- 개발·테스트 자동화에서 실제 광고를 클릭하거나 클릭을 유도하지 않는다.
- 새 광고 위치는 콘텐츠 흐름과 사용성을 해치지 않는지 검토한 뒤
  `AdPlacement`와 CSS를 함께 추가한다.

## 9. 보안과 개인정보

- `.env`, 토큰, 키, 인증서, 사용자 입력 샘플을 커밋하지 않는다.
- 외부 HTML을 그대로 렌더링하지 않는다.
- URL, 클립보드, 저장소 값은 신뢰하지 않고 길이와 형식을 검증한다.
- 사용자 입력을 분석하기 위해 외부 서비스로 전송하려면 먼저 화면에 알리고
  명시적인 동의를 받는다.

## 11. 검색 유입과 기능 추가 정책

캠툴의 새 기능과 기존 기능 확장은 검색량 자체가 아니라 사용자가 검색 후 한
페이지에서 문제를 해결할 수 있는지를 기준으로 결정한다.

### 검색 의도 정의

- 기능 작업 전 대표 검색 의도 하나와 보조 검색어를 한국어·영어별로 정의한다.
- 같은 입력과 결과를 원하는 검색어는 기존 도구의 설명·기능을 확장해 대응한다.
  별도 URL은 사용 목적이나 결과 형태가 명확히 다를 때만 추가한다.
- 한 URL은 하나의 대표 검색 의도를 우선하며, 서로 다른 도구가 같은 검색어를
  중심으로 경쟁하지 않게 한다.
- 검색 결과 제목은 사용자가 찾는 문제와 실제 제공 범위를 구체적으로 표현한다.
  화면의 브랜드성 이름과 검색 제목은 필요하면 분리하되 서로 다른 기능처럼
  오해하게 만들지 않는다.
- 검색량이 많아 보여도 캠툴의 즉시 사용·브라우저 처리 원칙과 맞지 않거나 결과의
  정확성을 보장하기 어려우면 구현하지 않는다.

### 페이지 구성

- 도구 페이지의 제목, 설명, 첫 입력 영역만 보고 무엇을 해결하는지 알 수 있어야
  한다.
- 각 페이지는 실제 기능 범위, 사용 방법, 계산 또는 변환 기준, 중요한 한계와
  개인정보 처리 방식을 짧고 고유한 문장으로 제공한다.
- 기능이 지원하지 않는 결과를 제목이나 설명에서 약속하지 않는다.
- 관련 도구 링크는 사용자의 다음 작업과 직접 연결되는 경우에만 제공한다.
- 새 공개 URL은 canonical, `hreflang`, sitemap, 도구 카탈로그와 구조화 데이터를
  같은 변경에서 확인한다.
- 한국어와 영어 제목·설명은 직역보다 각 언어의 실제 검색 표현을 우선하되 기능
  범위는 동일하게 유지한다.

### 가이드 콘텐츠 품질

- 가이드 URL은 기존 도구의 사용 결과를 해석하거나 실수를 줄이는 독립적인 질문이
  있을 때만 추가한다. 검색어 표현만 바꾼 유사 문서는 만들지 않는다.
- 한 가이드는 배경과 적용 범위, 실행 절차, 중요한 한계, 제출 전 체크리스트와
  실제 질문에 답하는 FAQ를 포함한다. 정해진 글자 수보다 독자가 다음 행동을 할 수
  있는지를 완료 기준으로 삼는다.
- 학교·학과·저널·제출 기관의 규정이 우선하는 주제는 일반 안내의 한계를 밝히고,
  계산기나 생성기 결과를 공식 증명처럼 표현하지 않는다.
- 한국어와 영어 문서는 동일한 해결 범위를 가지되 각 언어에서 자연스럽게 독립
  집필한다. 기계적인 문장 치환이나 원문 없이 번역 페이지만 대량 생성하지 않는다.
- 작성일이나 수정일을 구조화 데이터에 표시했으면 실제 내용 변경 때 함께 갱신한다.
- 가이드에서 관련 도구로, 도구나 홈에서 가이드로 이동할 수 있는 문맥상 내부 링크를
  제공하고 소개·개인정보처리방침·문의 링크는 전역 푸터에서 유지한다.
- 광고 심사 통과를 보장하는 문구를 사용하지 않는다. 광고보다 본문과 탐색이 먼저
  보이도록 하며, 콘텐츠가 없는 상태 페이지에 광고 슬롯을 추가하지 않는다.

### 출시와 측정

- 출시 전 대표 검색어, 현재 검색 결과 형태와 기존 캠툴 페이지의 중복 여부를
  기록한다.
- 초기 측정은 Google Search Console의 페이지별 노출, 클릭, CTR과 Cloudflare Web
  Analytics의 방문·기기·성능 지표만 사용한다.
- 방문 이후 실제 결과 생성 여부가 의사결정에 필요해질 때만 `tool_completed` 같은
  최소 제품 이벤트를 추가한다. 사용자 입력이나 파일 내용은 로그에 포함하지 않는다.
- 한 기능을 출시한 뒤 검색 노출과 사용성을 관찰하고 다음 기능을 진행한다. 검색
  유입만을 위해 유사 페이지나 얕은 콘텐츠를 대량 생성하지 않는다.
- 노출은 많고 CTR이 낮으면 제목과 설명을 먼저 점검하고, 방문은 많지만 사용성이
  낮으면 첫 입력 흐름과 모바일 화면을 먼저 개선한다.

### 검색 변경 완료 조건

- 대표 검색 의도가 도메인 사전 또는 제품 로드맵에 기록되어 있다.
- 검색 제목과 설명이 실제 제공 기능과 일치한다.
- 페이지에 기능 범위·한계·개인정보 처리 안내가 있다.
- 한국어·영어 메타데이터와 화면 문구가 함께 갱신됐다.
- canonical, alternate, sitemap과 내부 링크가 기존 URL 체계를 유지한다.
- 서버 렌더 결과에서 제목, 설명, H1과 구조화 데이터가 확인된다.
