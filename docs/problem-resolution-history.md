# 문제 해결 기록

기반 구현 중 사용자 진행을 손상시키거나 검증 신뢰도를 낮출 수 있었던 문제와 회귀 계약을 기록한다.

## SP-001 손상된 선택 이력이 정상 저장처럼 복원됨

- 증상·재현: 선택 횟수만 현재 노드와 맞춘 DB는 선택 ID, 도착 노드, 플래그가 원고와 달라도 복원됐다.
- 직접 원인: 저장 복원 시 이력 개수와 콘텐츠 버전만 확인하고 선택을 처음부터 재실행하지 않았다.
- 검출 실패 원인: 저장 테스트가 정상 이력, 트랜잭션 실패와 버전 불일치에 집중했고 내부 필드 변조 fixture가 없었다.
- 수정: 번들된 동일 버전 원고로 선택 이력을 순서대로 재실행해 선택 ID·도착 노드·플래그·현재 노드를 대조한다. 불일치 시 `invalid_save` 오류를 반환하고 원본 행은 보존한다.
- 해결 검증: 손상된 선택, 순서, 도착 노드, 플래그와 현재 노드 불일치 테스트를 추가했다. 손상 원본을 보존한 명시적 새 시작도 저장소와 양 플랫폼 UI 계약으로 고정했다. 엔진·저장소 테스트와 양 플랫폼 네이티브 스모크가 통과했다.

## SP-002 설계 도구가 Expo와 다른 React를 설치함

- 증상·재현: Mermaid CLI를 앱 개발 의존성에 두면 렌더러 패키지가 React 19.3을 설치해 Expo SDK 57의 React 19.2와 중복됐다. Expo Doctor가 중복 네이티브 의존성을 보고했다.
- 직접 원인: 모바일 런타임과 무관한 다이어그램 렌더러가 동일 `node_modules` 의존성 그래프에 포함됐다.
- 검출 실패 원인: 초기 설계 단계에는 Expo 앱이 없어 Mermaid 설치 직후 모바일 SDK 정합성을 검사할 대상이 없었다.
- 수정: Mermaid CLI를 앱 의존성에서 제거하고 고정 버전을 `pnpm dlx`로 격리했다. Expo가 요구하는 `react-dom` 19.2.3을 명시적으로 맞췄다.
- 해결 검증: `pnpm peers check`, `expo install --check`, Expo Doctor 21/21과 양 플랫폼 번들 생성이 통과했다.

## SP-003 적용된 마이그레이션 변경을 자동 검출하지 못함

- 증상·재현: 기존 SQL과 생성 TypeScript를 함께 다시 만들면 `db:check`가 통과해, 같은 migration 버전이 설치 시점에 따라 다른 스키마를 만들 수 있었다.
- 직접 원인: 생성 파일 동기화만 검사하고 적용된 migration 원문의 불변 해시는 보관하지 않았다.
- 검출 실패 원인: migration은 수정하지 않는다는 작업 절차를 자동 계약으로 고정하지 않았다.
- 수정: `src/storage/migrations.lock.json`에 파일별 SHA-256을 저장하고, 기존 파일 변경·삭제를 `db:build`와 `db:check` 모두에서 거부한다. 새 순차 migration만 추가할 수 있다.
- 해결 검증: 동일 파일과 신규 버전은 허용하고 변경·삭제·잘못된 잠금 형식은 거부하는 회귀 테스트를 추가했다.

## SP-004 검증 스크립트가 Expo Doctor 대신 pnpm Doctor를 실행함

- 증상·재현: `pnpm verify`의 마지막 `pnpm doctor`가 같은 이름의 package script가 아니라 pnpm 내장 진단을 실행했다.
- 직접 원인: 패키지 스크립트와 pnpm 내장 명령에 같은 이름을 사용하고 `pnpm run`을 생략했다.
- 검출 실패 원인: 개별 Expo Doctor 결과만 확인했고 통합 명령의 마지막 출력 주체를 구분하지 않았다.
- 수정: 스크립트를 충돌하지 않는 `sdk:check`로 변경하고 `verify`가 이를 호출하게 했다.
- 해결 검증: `pnpm verify` 출력에서 peer 검사, Expo install 검사와 Expo Doctor 21개 검사가 모두 실행되는지 확인한다.

## SP-005 여러 작품의 열기 버튼을 접근성 이름으로 구분할 수 없음

- 증상·재현: 카탈로그에 두 번째 작품을 등록하면 각 카드의 버튼이 모두 `이야기 열기`로 노출되어 스크린리더와 UI 자동화가 어느 작품을 여는지 구분할 수 없었다.
- 직접 원인: 화면에 보이는 작품 제목과 버튼의 접근성 이름이 연결되지 않았고, 공통 버튼이 별도 `accessibilityLabel`을 받을 수 없었다.
- 검출 실패 원인: 기술 fixture 하나만 있을 때는 같은 이름의 제어가 반복되지 않아 고유한 접근성 이름 계약을 검사하지 않았다.
- 수정: 공통 버튼에 선택적 `accessibilityLabel`을 지원하고 작품 카드는 `${release.story.title} 이야기 열기`를 전달한다.
- 해결 검증: iOS·Android UI 계약에서 제목이 포함된 버튼으로 최신 「작은 세계 우체국」을 선택하고 열한 번의 선택을 거쳐 엔딩을 보관하는 전체 흐름을 고정했다.

## SP-006 모바일 localhost 검사가 번들 요청 없이 대기함

- 증상·재현: iOS·Android 저장 스모크가 `exp://127.0.0.1:8081`을 열었지만 Metro는 IPv6 `::1`에만 대기해 번들 요청과 저장 검사 로그가 나오지 않는 경우가 있었다.
- 직접 원인: 호스트의 `localhost`가 IPv6를 먼저 해석했고, Expo가 시뮬레이터에 전달한 IPv4 loopback 주소와 Metro의 수신 주소가 달랐다.
- 검출 실패 원인: 이전 검증에서는 명령 앞에 Node DNS 순서 환경변수를 수동으로 지정해 통과했지만 프로젝트 실행 스크립트에 계약을 고정하지 않았다.
- 수정: 모든 `--localhost` 실행에서 별도 DNS 순서 옵션이 없으면 `--dns-result-order=ipv4first`를 자식 Expo 프로세스에 자동 적용한다. 저장 스모크는 같은 URL 재호출을 무시할 수 있는 기존 iOS·Android Expo Go 프로세스도 먼저 종료한다.
- 해결 검증: 환경변수를 따로 지정하지 않은 `pnpm ios:smoke`와 `pnpm android:smoke`에서 새 Expo Go 실행이 플랫폼 번들을 요청하고 `NATIVE_STORAGE_CHECK_PASS checkpoints=8`을 출력하는지 확인한다.

## SP-007 개발 전용 원고가 프로덕션 바이트코드에 남음

- 증상·재현: 프로덕션 화면은 빈 카탈로그를 보였지만 Hermes 바이트코드에서 `foundation-check`, `little-post-office`, 선택지 ID가 확인됐다.
- 직접 원인: 생성 모듈이 개발·정식 원고를 하나의 배열에 넣고 `createCatalog(false)`에서 런타임 필터만 적용했다.
- 검출 실패 원인: 프로덕션 카탈로그가 비었다는 단위 테스트만 있었고 최종 번들의 문자열 테이블을 확인하지 않았다.
- 수정: 생성 모듈을 정식 배열과 개발 배열로 나누고, 개발 배열 리터럴을 `__DEV__` 조건 안에 두어 Metro가 프로덕션 출력에서 제거하게 했다. 개발 원고 전용 표지도 같은 조건으로 불러온다.
- 해결 검증: iOS·Android 프로덕션 번들을 새로 생성하고 Hermes `-dump-bytecode`에서 세 개발 원고의 hash와 식별자가 모두 사라졌음을 확인했다. `pnpm build`가 모든 플랫폼 번들을 디스어셈블해 개발 릴리스 hash 누출을 자동으로 거부한다. 당시 개발 카탈로그 3개·프로덕션 카탈로그 0개 계약과 전체 테스트도 통과했다. v3와 표지 추가 뒤에는 개발 릴리스 4개의 hash와 표지 파일 hash가 모두 프로덕션 export에서 제외되는지 다시 확인했다.

## SP-008 AI 요청 입력이 실행 직전에 초기화됨

- 증상·재현: 제작실에서 AI 작업과 작가 요청을 선택하고 실행하면 busy 화면을 다시 그리는 순간 폼이 초기값으로 바뀌어, 실제 요청에는 기본 작업과 빈 brief가 전달될 수 있었다.
- 직접 원인: submit handler가 busy 상태를 먼저 렌더링한 뒤 새 DOM에서 작업과 brief를 읽었다.
- 검출 실패 원인: HTTP 테스트는 요청 body를 직접 만들었고 브라우저 mock 확인에서는 기본 작업을 사용해 폼 값 보존 여부가 드러나지 않았다.
- 수정: 선택 작업과 brief를 submit 시작 시 지역 변수로 캡처한 뒤 busy 상태를 렌더링하고, 캡처한 값을 API body에 사용한다.
- 해결 검증: 브라우저 JavaScript 구문·lint와 제작실 mock 흐름에서 선택한 이미지 연출 작업이 구조화 제안과 이미지 생성 단계로 이어지는지 확인한다.

## SP-009 모바일 제작실의 작품 목록이 문서 폭을 늘림

- 증상·재현: 제작실을 390×844와 320×720에서 열면 AI 패널 자체는 viewport 안에 있었지만, 가로 스크롤 작품 카드 두 개의 intrinsic width 때문에 `body.scrollWidth`가 462px까지 늘었다.
- 직접 원인: 820px 이하 단일 열 레이아웃에서 `work-rail`과 `work-list`가 grid item의 최소 콘텐츠 너비를 줄이지 못했다.
- 검출 실패 원인: 이전 모바일 검수는 헤더와 편집 버튼의 가시성을 확인했지만 문서와 개별 내부 스크롤 영역의 너비를 함께 비교하지 않았다.
- 수정: 모바일 grid track을 `minmax(0, 1fr)`로 만들고 작품 rail에 `min-width: 0`, `width: 100%`, `overflow: hidden`을 적용했다. 작품 목록만 자체 가로 스크롤한다.
- 해결 검증: 390×844와 320×720에서 document/body scroll width가 viewport와 같고 AI 이미지 생성·채택 버튼이 표시되는지 확인한다.

## SP-010 AI 제안 실패가 원장의 일부를 변경함

- 증상·재현: 잘못된 다음 장면을 포함한 제안에서 보낸 이와 본문이 먼저 바뀌고 연결 검사만 실패할 수 있었다. 다른 장면의 block ID도 덮어쓸 수 있었다.
- 직접 원인: 원장을 직접 수정하면서 뒤늦게 검증했고 ID 소유 장면을 대조하지 않았다.
- 검출 실패 원인: HTTP 테스트는 유효한 구조화 응답을 검사했지만 브라우저 적용의 실패 원자성과 충돌 계약은 없었다.
- 수정: 공유 순수 함수에서 복사본에 검증·병합하고 성공한 결과만 교체한다. 기존 조건·효과·ordinal을 보존한다. 작품·장면·revision이 달라진 비동기 제안은 적용하지 않는다.
- 해결 검증: invalid destination/cross-scene ID/배포본/잘못된 대상의 원본 보존, 순번·조건 보존 테스트를 추가했다. 브라우저에서 장면 변경 후 이전 제안이 사라지고 새 대상이 표시되는지 확인했다.

## SP-011 파일 없는 AI 연출 계획을 저장할 수 없음

- 증상·재현: AI 이미지 연출안을 draft에 적용해 planned asset과 cue를 만든 뒤 저장하면 파일이 ready가 아니라는 오류로 원고 전체 저장이 거부됐다.
- 직접 원인: 작업본 저장과 실행 패키지 export가 같은 완성 에셋 조건을 사용했다.
- 검출 실패 원인: 이미지 API 테스트는 구조화 제안과 시안까지만 확인했고 planned 연출의 실제 원장 저장은 확인하지 않았다.
- 수정: draft에서 전체 계획의 구조를 검사하되 실행 미리보기에서는 미완성 참조를 제외한다. 원장에 계획은 보존한다. 완성 에셋은 파일 hash·권리 정보, 본문 cue는 장면 소유권을 확인한다.
- 해결 검증: planned 원장 보존/preview 제외/엄격 export 거부/잘못된 channel 거부/ready hash·권리 거부/다른 장면 block 거부 테스트를 추가했다. localhost 브라우저 mock에서 계획 적용 → 검증 완료·모두 저장됨을 확인했다. 검증용 mock 행은 이후 제거해 원고를 복원했다.

SP-011 추가 조치: 새 수동 에셋은 ID별 `assets/planned/<id>.png` 예약 경로를 사용해
빈 경로의 UNIQUE 충돌을 피한다. 파일 없는 cue는 구조 검사용 placeholder를 거친 뒤
실행 패키지에서 제외하며 원장의 빈 경로를 임의로 바꾸지 않는다. ready/approved는

## SP-012 저장 대기 중 수정의 미저장 표시가 사라짐

- 증상·재현: 저장 요청 뒤 계속 편집하면 응답이 최신 원고까지 저장한 것처럼 dirty 상태를 지웠다. 삭제 후 새 본문·선택을 추가하면 행 개수 기반 ordinal이 기존 행과 충돌할 수 있었다.
- 직접 원인: 요청 당시 수정 버전을 보관하지 않았고 저장 버튼이 편집 시 다시 활성화됐다. ordinal은 행 개수로 계산했다.
- 검출 실패 원인: 정상 저장·재조회 흐름만 확인했고 대기 중 변경과 삭제 후 추가 경계를 포함하지 않았다.
- 수정: 스냅샷 revision과 로딩 순번을 대조하고 추가 수정은 dirty로 유지한다. 요청 중 중복 저장을 차단한다. 수동/AI 추가 모두 최대 ordinal을 사용한다.
- 해결 검증: 최대 ordinal의 삭제 후 추가 회귀 테스트와 타입·lint 검사를 통과했다. 브라우저 정상 저장과 잘못된 연결의 저장 차단을 확인했고, HTTP 회귀 검사에서 오류의 선택지·장면 ID 안내와 CSV 원본 보존을 고정했다. 느린 네트워크를 강제로 주입한 실제 경합 검증은 미실행이다.

SP-012 추가 조치: 브라우저와 테스트가 공유하는 session 모듈로 저장·불러오기 상태 전이를 분리했다.
지연 저장 중 추가 수정, 중복 제출, 다른 작품으로 이동한 뒤 응답, 순서가 뒤집힌 불러오기,
불러오는 동안 작성한 메모, 오래된 요청의 실패와 readonly 원장을 자동 검사한다.

## SP-013 오래된 탭이 최신 CSV 원고를 덮어씀

- 증상·재현: 같은 작업본을 연 두 탭에서 첫 탭이 저장해도 두 번째 탭은 자신의 오래된 원장을 그대로 PUT할 수 있었다.
- 직접 원인: 저장 요청에 서버 원장의 읽기 revision을 포함하지 않았다. CSV 10개도 파일별로 교체했다.
- 검출 실패 원인: 한 탭의 정상 저장과 released 보호만 테스트해 외부 편집·오래된 요청·파일 교체 실패를 다루지 않았다.
- 수정: 원장 내용을 hash한 revision과 expectedRevision으로 덮어쓰기 충돌을 차단한다. 새 CSV를 디렉터리 사본에서 만든 뒤 교체하고 실패 시 원본을 복원한다.
- 해결 검증: HTTP의 revision 누락 428·불일치 409·원본 동일성, 전체 파일 교체·실패 rollback·rollback 실패 시 backup 보존을 자동 검사한다.

## SP-014 연출 오류가 영문 내부 예외만 표시함

- 증상·재현: background cue를 voice로 변경한 뒤 저장하면 `Presentation cue channel differs from asset type`만 표시됐다.
- 직접 원인: 제작실 HTTP 경계가 런타임 검증기의 내부 영문 예외를 그대로 반환했다.
- 검출 실패 원인: 잘못된 next_scene_id의 한국어 오류만 검증했고 연출 연결 오류의 사용자 문구는 검사하지 않았다.
- 수정: 연출 종류/에셋 종류, 동작, 이미지 음량·반복 오류를 한국어로 안내하고 해당 cue ID를 유지한다. 미등록 선택 값은 편집기에서 보존해 수정할 수 있게 한다.
- 해결 검증: 순수 오류 변환과 실제 HTTP의 채널 불일치 오류·원장 보존을 자동 검사한다. 브라우저에서 voice로 바꾼 기존 이미지 참조가 미등록 값으로 남고 저장이 거부되는 것을 확인했다.

## SP-015 작은 제작실 화면에서 저장 상태가 숨겨짐

- 증상·재현: 320px·390px 제작실의 헤더에는 저장 버튼만 있고 미저장/저장 실패 상태가 보이지 않았다.
- 직접 원인: 모바일 CSS가 `.save-state`를 `display: none`으로 처리했다. `body`의 `overflow-x: hidden`도 세로 scroll container를 만들어 sticky 헤더가 문서 스크롤을 따라오지 못했다.
- 검출 실패 원인: 버튼 가시성과 가로 overflow를 검사했지만 저장 결과의 지속적인 표시를 계약에 넣지 않았다.
- 수정: 모바일 헤더를 두 행으로 배치해 저장 상태와 주요 버튼을 함께 표시한다. 가로 경계는 scroll container를 만들지 않는 `overflow-x: clip`으로 제한한다. 편지·생성 장면의 포커스 이동은 scroll margin을 적용해 sticky 헤더 아래에서 읽기 시작점을 가리지 않는다.
- 해결 검증: 320×720·390×844에서 미저장/완료 상태의 실제 가시성·문서 폭·저장 버튼 접근을 브라우저로 확인한다.

## SP-016 긴 장면 ID에서 자동 생성 본문 ID가 규격을 넘음

- 증상·재현: 규격상 허용되는 64자 장면 ID에서 본문 추가를 누르면 `-block-번호`를 붙인 ID가 64자를 넘는다.
- 직접 원인: 자동 ID 생성기가 접미사 길이를 고려하지 않았다.
- 검출 실패 원인: 현재 작품의 짧은 장면 ID만 사용했다.
- 수정: 번호 접미사의 길이를 먼저 확보한 뒤 접두사를 줄이고 원장 전체의 ID 충돌을 확인한다.
- 해결 검증: 64자 장면명에서 110개 생성, 두 자리→세 자리 번호 전환과 삭제 후 추가의 형식·중복 거부를 자동 검사한다. 새 장면 폼은 파생 ID 공간을 위해 장면 ID를 50자 이하로 안내한다.

## SP-017 원고 행 삭제가 연결된 조건·연출을 남김

- 증상·재현: 기본 폼에서 선택지/본문을 삭제하면 관련 조건·효과·cue는 남아 다음 저장에서 외래 키나 연결 검사를 실패했다. 직전 상태를 되돌리는 방법도 없었다.
- 직접 원인: 대상 배열의 한 행만 직접 제거하고 참조 관계와 원장 전체를 검사하지 않았다.
- 검출 실패 원인: 삭제 후 다음 ordinal 추가만 테스트했고 참조 cascade·마지막 행·도달 불가 장면·취소를 검사하지 않았다.
- 수정: 원장 사본의 관련 행을 정리하고 확인·전체 검증 뒤 교체한다. 마지막 본문/선택지·사용 중 에셋을 보호하며, 연결이 끊기는 장면 ID를 안내한다. 새 장면·검증된 삭제·선택 규칙 적용은 동일 편집 revision에서만 1단계 취소하고 원격 저장 revision을 유지한다.
- 해결 검증: 관련 조건·효과·cue·미사용 flag 정리, 공유 flag/에셋 출처 유지, 마지막 행/released 거부와 지연·후속 편집·새 로딩·저장 뒤 취소를 자동 검사한다. HTTP에서 call-sora 삭제 후보 200과 ask-sender 삭제 후보의 sora-answer 연결 오류 400을 고정했다. 브라우저의 마지막 본문/사용 중 에셋 차단, 연출 삭제 취소→승인→키보드 구조 취소→복원 저장을 확인했다.


## SP-018 앱과 제작 미리보기의 여러 배경 큐 처리 불일치

- 증상·재현: 같은 장면 진입에 show→swap 또는 show→hide를 등록하면 앱은 첫 이미지,
  제작 미리보기는 마지막 큐를 사용해 결과가 달랐다.
- 직접 원인: 앱은 첫 show 계열을 찾았고 제작실은 ordinal 정렬 뒤 마지막 background를 찾았다.
- 검출 실패 원인: 기존 원고는 장면당 배경 큐가 하나뿐이었다.
- 수정: 공통 순수 해석기로 마지막 진입 배경을 선택하고 hide/fade_out은 배경을 비운다.
  현재 정적 표시 계약이며 시간에 따른 fade 재생이나 이전 장면 배경 유지는 구현하지 않았다.
- 해결 검증: 역순 원장, show→swap, hide/fade_out, 다른 채널, cue 없는 장면,
  원본 불변성을 자동 검사한다. 네이티브 화면은 같은 해석기를 사용한다.


## SP-019 검수 화면에 미저장 변경 전의 제작표가 남음

- 증상·재현: 원고에서 선택지나 연출을 수정한 뒤 검수 탭을 열면 현재 행 개수와
  마지막 불러오기/저장의 제작표가 함께 표시되어 검사 대상이 모호했다.
- 직접 원인: 편집 테이블과 과거 `current.preview`를 한 화면에 사용했다.
- 검출 실패 원인: 검수 화면은 저장 직후에만 확인했다.
- 수정: 명시적 현재 원고 검수와 검수 당시 스냅샷·식별값·시각을 분리한다. 검사 이후
  수정은 이전 검수로 표시하고 내보내기를 차단한다. 늦은 응답은 적용하지 않는다.
- 해결 검증: 미저장 사본·원본 불변·후속 편집·로딩·오래된 오류·중복 요청·실패 시 보존을
  공유 순수 모듈의 지연 Promise로 검사한다. HTTP의 동일 원장 hash/UTC 시각을 대조한다.
  브라우저 확인 결과는 구현 검증 문서에 기록한다.


## SP-020 선택 규칙 적용 후 키보드 포커스가 본문으로 사라짐

- 해결 검증: 관련 브라우저 검사에서 규칙 적용/취소·대상 버튼 포커스·모바일 위치를 확인한다.

## SP-021 복제 목록 반영 실패 후 미등록 작업 폴더가 남음

- 검출 실패 원인: 기존 복제의 정상 경로만 확인했으며 파일 게시 실패와 stale 원고를 다루지 않았다.
- 수정: 원본 revision을 비교해 누락428/불일치409로 거부한다. 전체 CSV를 임시 폴더에서 작성한 뒤

SP-021 추가 조치: 복제201 뒤 목록 읽기만 실패하면 이미 생성된 원고를 다시 게시하지 않는다.

## SP-022 외부 파일 오류 때문에 제작실에서 원고를 열 수 없음

- 증상·재현: 임시 작업 원장의 CSV에서 다음 장면을 없는 ID로 바꾸면 GET 전체 검사가
  실패해 오류를 고칠 원고 폼 자체가 열리지 않았다. 파일 변경으로 ready 이미지의 해시가
  맞지 않아도 같은 불러오기 검사 경로를 거친다.
- 직접 원인: 읽기와 저장의 전체 분기/에셋 검증을 동일하게 성공 조건으로 사용했다.
- 검출 실패 원인: 유효한 원고를 불러온 뒤 잘못된 편집의 저장 거부만 검사했다.
- 수정: CSV 형식과 작품 identity가 맞으면 읽기는 원장/revision과 오류 안내를 반환한다.
  저장·실행 미리보기·검수는 계속 전체 검증을 요구한다. 오류가 있는 원고도 기본 폼에서
  수정할 수 있고 정상 저장 후 안내를 지운다. 형식/identity 손상을 무조건 허용하지 않는다.
- 해결 검증: HTTP에서 손상 원고 읽기200→원본 revision을 사용한 수정 저장200→오류 해제를
  검사했다. 실제 임시 제작실320px에서도 잘못된 연결 표시→수정→Enter 저장을 완료했다.
  관련 자동 검사와 전체 빌드는 통과했다. 원본 프로젝트 원장은 보존했다.


## SP-023 수정·새 로딩 뒤 미리보기의 오래된 오류가 표시됨

- 증상·재현: 미리보기 요청을 보낸 뒤 원고를 수정하거나 새 원고 불러오기를 시작하고,
  이전 요청을 실패시키면 예전 검사 오류가 새 편집 상태의 오류로 나타날 수 있었다.
- 직접 원인: 기존 미리보기 오류 분기는 요청 sequence만 대조했다. 편집 revision과
  loadSequence를 함께 확인하지 않았으며 늦은 결과의 포커스 이동도 최종 렌더와 결합돼 있었다.
- 검출 실패 원인: 기존 preview 테스트는 엔진 경로의 정상/잘못된 선택만 검사했다.
- 수정: 브라우저와 Node가 공유하는 playtest 세션으로 요청/원고/load 순번을 대조한다.
  오래된 성공·실패를 무시하고 새 요청의 busy 상태를 보존한다. 최종 렌더 뒤에만 정상 읽기
  포커스를 이동한다. 경로 내보내기도 같은 현재 원고 조건으로 보호한다.
- 해결 검증: 지연 Promise의 수정/로딩·늦은 성공/실패·중복·reset·재시도를 자동 검사했다.
  실제 브라우저320/390/1280px에서 정상 선택·이전 선택·원고 수정 후 잠금·미저장 기록 복사,
  읽기/대화상자 종료 포커스를 확인했다. 실제 브라우저 지연 주입은 미실행이다.


## SP-024 오래된 AI 설정 조회가 새 연결 상태를 덮음

- 증상·재현: 설정 GET을 지연한 뒤 저장/삭제를 완료하면 이전 GET이 새 연결 상태를 덮을 수 있다.
  초기 설정 GET 실패도 정상 원고 로딩과 같은 Promise.all catch로 들어가 전체 제작실 오류로 표시했다.
- 직접 원인: 설정 조회/변경에 순번·공통 busy 상태가 없고 설정 실패를 원고 로딩 실패와 묶었다.
- 검출 실패 원인: 설정의 정상 조회와 잘못된 키 거부만 검사했고 응답 역전·중복/실패 복구를 포함하지 않았다.
- 수정: 공유 설정 세션에서 최신 응답만 반영하고 변경 중 중복/읽기·닫기·입력을 차단한다.
  설정 실패와 원고 로딩을 분리하고 dialog 종료 시 키 입력을 비운다.
- 해결 검증: 이전 GET→변경 성공→늦은 GET, 변경 중 중복 거부, 늦은 오류/최신 lock 유지,
  실패 뒤 metadata 보존·재시도를 주입 callback으로 검사한다. 실제 사용자 키/Keychain 쓰기는 하지 않았다.
  브라우저 결과는 구현 검증 기록에 남긴다.
